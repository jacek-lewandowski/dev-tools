# Brief: install the standard Claude Code plugins in every sandbox

Date: 2026-10-28. Task brief, no phase plan. The implementer takes it directly;
one review follows. Evidence file: `docs/superpowers/evidence/2026-10-28-claude-plugins.md`.

## Goal

Every sandbox has these Claude Code plugins installed and enabled at user
scope, without anyone running `claude plugin install` by hand:

- `superpowers@claude-plugins-official`
- `frontend-design@claude-plugins-official`
- `code-simplifier@claude-plugins-official`
- `playwright@claude-plugins-official`
- `claude-md-management@claude-plugins-official`

## Known facts (spiked on 2026-10-28 with Claude Code 2.1.302)

- `~/.claude` in the container is a bind mount of the per-sandbox directory
  `$SANDBOX_DIR/.claude` (seeded from the host's `~/.claude` at creation). A
  plugin installed into the image's home at build time is hidden by that
  mount, so the install has to happen at container start, inside the mounted
  home, from the entrypoint (`entrypoint.sh`, generated by
  `create-ai-sandbox.sh`, runs as the sandbox user; the agy-grants section is
  the pattern: merge state at every start, never fail the start).
- In a fresh `~/.claude` the marketplace `claude-plugins-official` is not
  known. `claude plugin marketplace add anthropics/claude-plugins-official`
  clones it over HTTPS with no account; re-running it on an existing
  marketplace prints "already on disk" and exits 0 in 0.5 s.
  `claude plugin marketplace update claude-plugins-official` refreshes the
  clone (1.3 s with network); a stale clone makes `install` fail with
  `not_found`.
- `claude plugin install <name>@claude-plugins-official -y --json` works
  non-interactively with no account, exits 0 and prints `"outcome":"ok"`;
  on an already installed plugin it exits 0 with "already installed" in
  0.6 s. It records the install under `~/.claude/plugins/` and enables the
  plugin in `enabledPlugins` of `~/.claude/settings.json`.
- All five plugins exist in the marketplace; none declares a
  marketplace-declared command or a `userConfig`.
- `claude plugin install` on a plugin that is installed but disabled
  re-enables it (spiked: disable, install, `enabled` flips back to true). So a
  blind install at every start would undo a user's `claude plugin disable`.

## User decisions

- The plugin list lives once, as a constant in `create-ai-sandbox.sh` beside
  the other constants, rendered into the entrypoint; a later plugin is added
  there and nowhere else.
- At every container start the entrypoint, as the sandbox user: ensures the
  marketplace is added, then installs, with `-y`, only the listed plugins
  whose id is absent from `claude plugin list --json`; a plugin that is
  present, enabled or disabled, is left alone, so `claude plugin disable`
  survives restarts. The marketplace is updated only when at least one
  plugin has to be installed. Every step tolerates failure (no network, CLI missing) and logs to
  `/tmp/claude-plugins.log`; the start never fails and is not delayed by a
  network step the shell has to wait for, so run the section in the
  background the way other services in the entrypoint are started, or prove
  it stays under a second when everything is already present.
- `sandbox-doctor` gets a status line listing which of the required plugins
  `claude plugin list --json` reports as installed and which are missing.
- The tool notes block in `create-ai-sandbox.sh` mentions the plugins in one
  line. `PROJECT_MAP.md` and the `create-ai-sandbox.sh` entry in it stay
  accurate; the README gets one sentence if it lists what the image provides.

## Obligations (tests and acceptance)

- P1 `tests/ai-sandbox/test-tools.sh` (or a new `test-plugins.sh` in the same
  harness): the generated `entrypoint.sh`, run against a stub `claude` on
  `PATH` that records its arguments and answers `plugin marketplace list
  --json` and `plugin list --json` from fixtures, and with `exec "$@"`
  pointed at `true`: with an empty plugin list it adds the marketplace,
  updates it and installs all five plugins with `-y`; with a list fixture
  where one plugin is installed and enabled and another installed but
  disabled, it installs only the three missing ones and never calls install
  for the two present; and it exits 0 even when the stub fails every command.
  Expected: the suite passes.
- P2 text assertions on the generated `entrypoint.sh` and `sandbox-doctor`:
  the five plugin ids appear exactly once in the generated image build
  directory as a rendered list (the search that enumerates them), and the
  doctor status line exists. Expected: pass.
- P3 real run in this sandbox: execute the plugin section of the generated
  entrypoint (or the equivalent commands it renders) against the real
  `~/.claude`, then `claude plugin list --json` shows the five plugins
  enabled at user scope. Record the output.
- P4 `bash tests/ai-sandbox/run-tests.sh` stays green, with the pre-existing
  SDKMAN case noted as in the gitleaks brief.

Acceptance: P1 through P4 evidenced in the evidence file with the actual
command output and the commits. The image itself needs a host re-run of
`create-ai-sandbox.sh` to pick up the new entrypoint; that is the user's step
and is stated in the report, not performed.
